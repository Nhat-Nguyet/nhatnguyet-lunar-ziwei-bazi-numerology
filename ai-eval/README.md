# AI evaluation set: can a language model compute the lunar calendar?

1,520 questions in English, Vietnamese and Chinese whose answers are **computed**, not
opinions: the Vietnamese lunar date of a day, the date of Tết, the stem-branch of a day
or a year, the solar term on a date and its exact minute, the Life palace, bureau and
star positions of a Zi Wei Dou Shu chart, the four pillars of a BaZi chart, and two
numerology numbers. Every answer comes from the Nhat Nguyet engine, the same code that
passes the shared test vectors in [`../ca-kiem`](../ca-kiem).

Data: Nhat Nguyet (nhatnguyet.org). Licence: [CC BY 4.0](../DATA-LICENSE).

## Why

Ask a chat model "what is the lunar date of 21 January 1985?" and it will answer at
once, in the tone it uses for facts. The answer is arithmetic over new moons and solar
longitudes, and a model that has not run that arithmetic is guessing. Two things make
the guess worse for Vietnamese users:

- **Vietnam's calendar is not China's.** The rules are the same but the day is decided
  in Vietnam time (UTC+7), not Beijing time (UTC+8). Between 1900 and 2100 the
  Vietnamese lunar date differs from the Chinese one on **2,724 days**, and Tết falls on
  a different day in **9 years** (1985 by a whole month). Most of what a model has read
  is about the Chinese calendar.
- **Boundaries decide the result.** A BaZi month changes at a solar term to the minute,
  the year at Start of Spring, the day at 23:00. A model that is right "most of the
  time" is wrong exactly for the people born near those moments.

This set measures how often a model gets these facts right, and the hard half is built
from exactly those traps. The point it is meant to make: **a model should call a
deterministic tool**, such as the [`@nhatnguyet/mcp`](../js/packages/mcp) server, and
quote its result, instead of computing calendars in its head. Running the set twice,
once with no tools and once with the MCP server, shows the difference.

**Hard cases** (each carries a `hard_case_reason`):

- `lunar_date`, `ziwei_*`: days where the Vietnamese and Chinese lunar dates differ,
  taken from the published day-by-day comparison with lunar-javascript in
  [`../doi-chieu`](../doi-chieu) (`khac-ngay-am.csv`); the reason quotes the Chinese date a
  Chinese-calendar library gives. Also leap-month days and births after 23:00.
- `tet_date`: the 9 years where Tết differs, asked for both Vietnam and China.
- `year_pillar`: dates between 1 January and Tết, which still belong to the previous
  lunar year (some of them already past Start of Spring, where the BaZi year changes).
- `solar_term_on_date`: the day a term starts and the day before it.
- `solar_term_moment`: terms that start in the last hour before midnight in Vietnam, so
  the date is different in Vietnam (UTC+7) and China (UTC+8).
- `bazi_pillars`: births 3 to 120 minutes before or after Start of Spring or another
  sectional term, and births after 23:00.
- `numerology`: results where reducing day, month and year separately (a common
  shortcut) gives a different Life Path, and master numbers 11, 22, 33.

Each question states its conventions (time zone, how the double hour and leap months are
counted, where the BaZi year and day change), so a correct answer is well defined. They
are the conventions of the Nhat Nguyet libraries; other schools differ on some of them,
and the question says which one to use.

## Format

`questions.jsonl`, one JSON object per line:

| Field | Meaning |
|---|---|
| `id` | `<task>-<4 digits>`, stable for a given version |
| `task` | one of the tasks above |
| `difficulty` | `easy` or `hard` |
| `tool` | the `@nhatnguyet/mcp` tool that answers it |
| `input` | the question's data in machine form (date, time, gender, year...) |
| `question_en`, `question_vi`, `question_zh` | the same question in three languages, each asking for a JSON answer |
| `answer` | the reference answer, structured; names in `vi`, `en` (pinyin) and `zh` |
| `answer_text` | the reference answer as one English sentence |
| `hard_case_reason` | why the item is hard (hard items only) |

Example (shortened):

```json
{"id": "tet_date-0001", "task": "tet_date", "difficulty": "hard", "tool": "lunar_convert",
 "input": {"lunar_year": 1903, "calendar": "VN"},
 "question_en": "On which Gregorian date does lunar new year (day 1 of month 1) of lunar year 1903 fall in the Vietnamese lunar calendar, computed for Vietnam time (UTC+7)? Answer with JSON {\"date\": \"YYYY-MM-DD\"}.",
 "answer": {"date": "1903-01-28"}, "answer_text": "1903-01-28.",
 "hard_case_reason": "Vietnam and China celebrate this lunar new year on different days: 1903-01-28 in Vietnam, 1903-01-29 in China."}
```

## How to run

1. Send each question (in the language you want to test) to your model and keep its
   reply. Write one line per question to `answers.jsonl`:

   ```json
   {"id": "tet_date-0001", "answer": {"date": "1903-01-28"}}
   {"id": "day_pillar-0001", "answer": "Sure! The day is {\"pillar\": \"Giáp Thân\"}"}
   ```

   `answer` may be the JSON object the question asks for or the model's raw reply; the
   scorer takes the first JSON object in it.

2. Score:

   ```bash
   python3 ai-eval/score.py answers.jsonl            # table by task, easy and hard
   python3 ai-eval/score.py answers.jsonl --json summary.json
   ```

   Names are matched through the [terminology dataset](../du-lieu/terminology): "Jia Shen",
   "Giáp Thân", "Giap Than", "甲申" and "jiǎ shēn" are all the same pillar. Vietnamese
   without diacritics is accepted only when it is not ambiguous ("Ty" could be Tý or
   Tỵ, so it is not). Solar-term moments are right within one minute (the engine is
   within 0.9 minutes of IMCCE, see [`../doi-chieu`](../doi-chieu)). Missing answers count
   as wrong. Standard library Python 3.9+, no network.

3. To let the model use the tool instead, give it the MCP server
   (`npx -y @nhatnguyet/mcp`, see [its README](../js/packages/mcp)) and run the same
   questions.

## Reproducing and checking

```bash
cd thu-vien-mo
node --conditions=source ai-eval/generate.mjs            # rebuild questions.jsonl and the table above
node --conditions=source --test ai-eval/check.test.mjs  # same bytes, well formed, scorer self-test
python3 ai-eval/score.py --self-test                     # reference answers score 100% in vi, en, zh
```

The generator is deterministic (fixed seed, no network, no model calls). It needs the
TypeScript sources in `js/` (run `npm install` there once). Because every answer is
recomputed from the engine, a change in the engine that changes an answer shows up as a
failing check until the set is regenerated.

**Limits.** The reference is the Nhat Nguyet engine, checked against NASA new moons and
IMCCE solar longitudes; a disagreement with another calendar is not automatically an
error on either side. Chinese-calendar answers (`tet_date` with `"calendar": "CN"`,
`solar_term_moment` at UTC+8) come from the same engine at UTC+8; the five months where
that differs from lunar-javascript's historical corrections (1914, 1916, 1920, 2057,
2097) are left out, and the 9 Tết years are checked against lunar-javascript.
